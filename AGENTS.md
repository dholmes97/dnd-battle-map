# Project direction

- Prefer a lightweight hexagonal boundary: keep battle-map rules and deterministic decisions in framework-free shared modules with direct unit tests, while React, Worker/D1, and browser APIs remain adapters around that core.
- Keep React behavior split into cohesive feature hooks/components with Vitest and Testing Library contracts; reserve source-pattern assertions for structural wiring that cannot be observed behaviorally.
- Treat cohesive, high-resolution full-scene maps as the only map-authoring workflow. Do not restore the retired generic terrain or fragment-based editor.
- Render every full-scene base map at 128 source pixels per five-foot cell so larger grids retain the same zoom detail as 24×16 maps; version asset filenames whenever the image bytes change so immutable browser and R2 caches cannot serve stale art.
- Keep base-map identity and canonical metadata in the durable `map_images` catalog. An encounter's active map and private draft reference that catalog entry; never duplicate or edit the base-map name, description, biome, mood, asset path, or dimensions inside encounter setup JSON.
- Keep Map Workshop's base-map chooser in a compact independently scrolling list so preparation tools stay nearby. Do not offer separate structural wall, door, or window annotations; use vision walls and vision doors for sight, and represent a window by leaving a gap between vision-wall segments.
- Put the server-backed encounter Draft section at the top of Map Workshop's independently scrolling sidebar; do not expose preset libraries or redundant file Export/Import controls. Before changing to a different base map, warn when the current draft has unsaved changes, because switching maps would discard prepared vision geometry and annotations. Label the shared-fog default-eight-corner action Reset fog and confirm before replacing custom corners.
- Enable Apply Draft only when the current draft differs from the map already applied to the encounter; undoing edits back to the applied map must disable it again.
- Match Map Workshop undo and redo to the player map: compact icon buttons in the top header plus Cmd/Ctrl+Z, Cmd/Ctrl+Shift+Z, and Ctrl+Y shortcuts, without intercepting shortcuts while editing fields. Do not duplicate large history buttons in the left controls.
- Require explicit confirmation before discarding an encounter map draft, with a warning that its prepared vision walls, doors, round blockers, labels, and notes will be permanently replaced by the active map.
- Do not restore the retired matched-addition/sticker workflow; cohesive base maps stand on their own.
- Keep the current base map compact in Map Workshop and reveal the full chooser only after an explicit Change base map action. Keep Label and DM Note as compact top-toolbar tools. Label placement and editing are direct and WYSIWYG: choose Label and click or keyboard-activate a map location to type in a field exactly matching the final label geometry, or click an existing label to edit its text and Everyone/DM-only visibility; press Enter to save or Escape to cancel, and do not require a distant sidebar text field. Create and edit DM notes through an anchored private-note editor on the map as well; clicking an existing note marker or its sidebar entry reopens it. Do not show the workshop keyboard cursor merely because the map received pointer focus—reveal it only after actual keyboard navigation.
- Keep the battle map visually dominant: desktop layouts must fit the map within the browser viewport, with controls and sidebars scrolling independently when needed.
- Keep global map launchers in the compact top toolbar; do not duplicate creature-palette or map-workshop controls in the right sidebar.
- Keep per-participant undo and redo durable and server-authoritative. Present both as compact top-toolbar icons, with Cmd/Ctrl+Z for undo and Cmd/Ctrl+Shift+Z plus Ctrl+Y for redo; never intercept these shortcuts while editing a field.
- Keep auto-expiring pings and DM spotlights out of Undo/Redo, including when rebuilding stacks from legacy action rows; only durable drawings are reversible annotations. When a newer shared edit prevents undo or redo, identify the affected move, HP, initiative, effect, drawing, placement, or token edit instead of showing a generic shared-state conflict.
- Keep tactical toolbar modes active after each use, including Ping, Draw Line, Erase, and DM spotlights; participants explicitly choose another tool when finished.
- Suppress native browser drag ghosts for spell placement. The transparent, locally animated map preview is the only spell artwork that should follow the pointer.
- Use one aligned X glyph system for close, discard, and compact removal actions, with styling matched to meaning; use a trash glyph for destructive list-item deletion instead of an ambiguous X.
- Treat initiative as a shared turn window: matching monster packs receive one durable group initiative by default—even when the DM edits a member card or corrects initiative during combat—and a character plus their summons always share one turn. Show exactly one player turn-ending action: End Turn for a lone token or End Group Turn when multiple tokens share the slot. Members can act in any order; offer an explicit Split from group action for exceptions.
- Keep token detail cards focused on repeatedly actionable information and never show initiative on the card. Edit initiative inline from the roster value or missing-value dash; Enter or blur saves, Escape cancels, and editing a grouped row updates the whole initiative group.
- Keep token detail summaries compact: identify them as `Kind: Controller`, leave creature size in Edit details, keep Temp HP beside HP in the top stat row, and place `+ Effect` directly after the existing effect chips instead of giving either control a separate row.
- Keep combat history out of the right sidebar: launch a scrollable Combat Log from a compact top-toolbar icon, and keep each roll's detail line at least as large as its title line so the history remains readable. Keep DM turn correction there as well by making the Round control open the round and active-group editor; players see the same Round display without editing authority.
- Use one local one-card lock model for both players and the DM: a lock control in the top-right of any creature or spell card docks it at the bottom, later selections stack directly above it, locking another card replaces the prior lock, and unlocking returns to the ordinary single selected card. Default each player to their own character being locked when the encounter opens; the DM starts without a locked card. Do not add redundant “Your character” or “Locked card” badges—the icon is the indicator—and let the initiative roster scroll rather than displacing the cards.
- Keep HP changes explicit: an empty amount performs no action, invalid or missing input is visibly required, and a successful Damage or Heal action clears the amount for the next use.
- Track token altitude durably and independently from ground movement. Controllers may edit it as a plain whole-foot text value or adjust it in five-foot steps with the wheel or Page Up/Page Down while dragging; show positive altitude on the map and make move-plus-altitude changes one undoable action. Do not expand cards with transient destination coordinates or distance while dragging.
- Show walking speed directly on token cards and expose non-walking fly, swim, climb, and burrow speeds only through the Speed value's accessible hover/focus detail.
- Preserve every rapid turn-advance click: paint each advance immediately, but serialize its authoritative request so repeated DM advances skip the intended number of initiative slots instead of collapsing onto one stale server turn.
- Size the desktop map from its live CSS container; observe that stable layout container rather than the canvas whose backing dimensions are mutated during rendering, do not freeze dimensions from an early JavaScript layout measurement, and explicitly stretch the desktop grid column so the base flex layout's centered content rule cannot shrink-wrap it.
- Make Map Workshop reuse the player map's shared Fit geometry: derive one square cell size from the live canvas container, center the complete scene with letterboxing as needed, and use the same geometry for drawing and pointer coordinates.
- Cache the rendered full-scene map by stable map-package content rather than response-object identity. Ordinary live encounter updates must not recreate or reload unchanged scene assets. Draw the high-resolution base image directly into the viewport rather than first copying it into a full-resolution backing canvas that can exceed Safari's canvas-area limit.
- Keep fog of war as a durable scenario map setting with three DM-selectable modes: off, shared DM-controlled polygon fog, and dynamic per-player vision. The DM always sees the full map; players receive server-filtered tokens and annotations even though their browser also receives bounded vision geometry for immediate local painting.
- Mirror the party-map header in Map Workshop: keep visibility mode, its contextual fog tools, and history in outlined groups on the left; center the base-map identity with the Map Workshop · Draft label; and present Discard Draft, Apply Draft, and Return as compact, clearly labelled icon actions on the right. Ordinary Select is the universal workshop cursor for additions, labels, notes, shared-fog corners, and dynamic vision blockers; do not restore a separate fog-select mode or a left-column visibility panel.
- Let the DM prepare shared-fog corners and dynamic walls, doors, and round blockers privately in Map Workshop. Start shared fog with corners plus a midpoint on every side, allow corners to be added and removed down to a three-point minimum, and keep its corners directly draggable during play. Dynamic blockers are free-angle rather than grid-snapped: selected walls and doors can be translated or reshaped from either endpoint, while selected round blockers can be moved from their interior and resized from their rim. Reveal the footprint of a round blocker once a player can see its surface, while keeping its shadow opaque so the tree, column, boulder, or statue remains identifiable. Dynamic doors must be openable and closable during play. Vision guides are DM-only, player fog masks are fully opaque, and guide edits must not force the large scene canvas to rebuild.
- Short-circuit unchanged live-state polls before loading encounter collections or calculating vision polygons. Bound fog geometry so dynamic sight remains responsive even on heavily annotated maps.
- Keep unchanged visible encounter polling activity-aware: back off to at most 750ms during active combat or about eight seconds during setup and deliberate pause, then restore the fast 250ms cadence after a changed version, page focus, or restored visibility. Preserve deterministic participant-specific jitter wherever the ceiling is at least one second.
- Correlate browser encounter requests with bounded operation IDs and server-generated request IDs. Echo the operation ID, publish total and projection `Server-Timing`, and emit privacy-safe structured completion records that classify outcomes, bounded projection sizes, and latency; deterministically sample unchanged polls at 1:32 so diagnostics do not recreate the hot-path load they measure.
- Freeze dynamic player vision at the last server-authoritative geometry throughout token dragging and while a move is pending. Moving a local token preview must never reveal terrain; replace vision only when the authoritative move response arrives, and reveal nothing from a rejected move.
- Preserve the map navigation convention: the desktop viewport fills the entire available stage, 100% uses a centered cover view with square grid cells, the dedicated Fit control or zooming out from 100% enters a whole-map Fit view (the only letterboxed state), the zoom readout always shows the effective percentage while the highlighted Fit icon indicates Fit mode, mouse-wheel and trackpad-pinch gestures zoom toward their focus point, and left-dragging empty map space reveals cropped edges while token dragging remains direct; do not require right-click. Keep Presentation mode visually distinct from Fit.
- Keep phone fixes touch-specific so desktop interaction does not regress. On narrow or coarse-pointer layouts, keep a persistent safe-area Exit presentation action, use explicit two-pointer pinch zoom without also committing a one-finger pan or token drag, and never reveal or retain the keyboard map cursor because of touch focus or pointer input.
- The DM must be able to press and immediately drag any visible token on the map without selecting its sidebar card first.
- Keep selection independent from movement authority: every participant may select and inspect any visible token directly on the map. A durable scenario-specific DM-only Strict movement switch controls only dragging—on limits players to their character and summons; off lets anyone drag any visible token—while ownership continues to govern HP, initiative, editing, and dismissal.
- Keep the compact top-toolbar UI Settings menu separated by scope: Your display contains browser-local grid visibility plus positively worded Colored token centers and Health rings toggles, both enabled by default, while a DM-only Encounter settings section contains shared controls such as Strict movement. Never leave Strict movement permanently visible in the sidebar. Local visual controls must redraw immediately without shared-state traffic; turning Colored token centers off reveals the terrain and removes the inner ownership ring while preserving HP, selection, and effect indicators unless Health rings are separately turned off.
- Token moves, placements, and deletions must never globally block the map while awaiting confirmation. Preserve optimistic per-token mutations, reconcile them with authoritative responses, and roll back only the rejected token action.
- Treat repeated token drags during one active turn as revisions of a single move: persist the first-drag origin, measure every later destination from it, replace rather than accumulate movement used, and clear the origin only when that initiative slot becomes active again or combat is reset.
- Apply that optimistic rule to every battle-map interaction: annotations, initiative, HP, effects, token details/visibility, combat controls, encounter state, and local undo/redo must render immediately for the initiating participant while pending reducers survive live refreshes; synchronously commit the initiating paint before starting the network request, reconcile to authoritative state, and roll back only rejected mutations.
- Keep `useEncounterSync` operation-oriented: pending mutations, command sequences, and local history refs are private synchronization internals. Keep canvas drag/drop, pointer, pan, zoom, drawing, and fog-edit gesture orchestration in `use-battle-map-gestures` rather than the root map component.
- Make encounter-state controls self-explanatory and tactile: keep Start/Restart, Advance, Pause/Resume, and Reset in one compact four-icon row directly beneath the DM identity at the top of the sidebar, with descriptive hover/focus tooltips and accessible names. Do not restore the token-roster search field. Pause explains that it preserves combat state, Reset requires explicit confirmation and states what it clears, and both show pressed plus pending feedback.
- Starting combat from setup may act immediately, but restarting active or paused combat always requires confirmation that round, turn order, movement, and completed-turn tracking will reset.
- Restart and Reset controls always explain their distinct effects on hover and keyboard focus: Restart returns to round 1 with current initiative; Reset exits combat to setup. Both preserve map, tokens, HP, effects, and initiative values.
- Route every authored blocking dialog through the shared modal lifecycle: intentional initial focus, topmost-dialog Tab/Shift+Tab containment, inert background content, explicit per-dialog Escape/backdrop policy, and exact opener focus restoration across keyboard and pointer launchers. Required acknowledgements such as concentration checks must not dismiss through Escape or the backdrop.
- Reserve full-screen shadowbox dialogs for cinematic handouts and genuinely blocking acknowledgements. Present combat-roll results, applied-damage updates, and DM damage adjudication as compact translucent edge cards that preserve the battlefield; queue simultaneous activity in a bounded visible stack and keep overflow discoverable. Put DM approval for a player-originated damage roll in a final row of that same live roll card, after the damage reveal, and show a standalone approval card only as a recovery path when the matching roll card is unavailable because it was dismissed, overflowed, refreshed, or reconnected. Auto-dismiss a completed miss after ten seconds and an adjudicated roll after three seconds, counting down visibly in unobtrusive footer space; pause that local countdown while the card is hovered or keyboard-focused, and preserve the event in the Combat Log.
- Treat every player-originated combat roll as a public encounter event: all joined participants receive the same attacker, target, action, individual dice, modifiers, total, outcome, and rolled damage regardless of token visibility. A DM-originated roll remains private to the DM until they release or override its hit/miss verdict; players then receive only that released verdict, and damage remains private until the DM chooses and applies the final amount. Apply that DM-selected damage immediately without creating a second approval card, reveal only the final damage total to the table, and keep exact AC, HP, raw dice, modifiers, adjusted damage, adjudication method, notes, and DM controls behind their server-authoritative privacy boundaries. Do not replay historical rolls as new edge cards when a participant joins or refreshes.
- Resolve attack and damage as two durable server-authoritative stages. A hit pauses after its shared verdict so the table can resolve reactions; create no damage dice or DM proposal until the original roller explicitly chooses Roll damage. All participants then receive the shared damage roll, while only the original roller sees that action (the DM retains a server-side authorization fallback). A miss ends immediately.
- Animate each visible die locally with a deterministic 4–7-value preview sequence derived from stable roll and die identity, slowing before the server-authoritative final value. Do not expose a fixed rhythm, announce preview values to assistive technology, or style advantage/disadvantage winners before every die has settled; reduced-motion users receive the final values immediately.
- Model automatic-damage combat actions explicitly: they skip the attack roll, Bless, AC comparison, and hit/miss verdict, then enter the ordinary separate damage-roll stage so their dice and any DM adjudication still follow the shared combat flow.
- Require an explicit shared-modal confirmation before permanently deleting a maintained character combat action; name the action and character in the warning, focus the safe Keep action choice first, and close the dialog only after a successful deletion.
- Keep DM damage approval compact and singular. Use `Void attack` for the explicit no-damage terminal ruling, do not present a redundant user-facing Cancel proposal action, and reserve the cancelled state for system cleanup and recovery paths.
- Keep combat rolling available in every campaign while preserving the isolated production Interaction QA campaign for authorized multi-client testing. Its fixed launcher offers one DM and two independently controlled player personas so three ordinary windows can test cross-player visibility; reset must restore both player characters and their attack-ready fixture data without invalidating any open persona sessions, and those windows must receive the reset through ordinary live synchronization. Treat an actual unauthorized participant response as an ended local session that returns to the appropriate launcher with a clear message, never as a transient reconnect loop. Do not restore the retired `off | qa | all` runtime gate or make the QA launcher depend on a combat feature flag.
- Clearing map annotations means clearing durable drawings only. Show the drawing count, require confirmation, preserve pings and spotlights, and record one bounded atomic snapshot so Undo restores and Redo re-clears exactly those drawing IDs without touching later work.
- Distinguish deliberate DM pauses from synchronization safety states in map messaging; never describe a DM-paused encounter as waiting for shared state to become current.
- Keep in-game chat durable and scenario-scoped, outside Undo/Redo, with an Everyone channel plus server-filtered private DM-to-player threads only. Launch it from the compact top toolbar with unread badges; use a movable, minimizable bottom-corner panel on desktop and a compact bottom sheet on mobile.
- Treat DM image handouts as scenario-scoped chat attachments with the same Everyone/private visibility rules. Prepare bounded display and thumbnail assets in the browser, preferring WebP with a storage-efficient JPEG fallback for Safari, discard originals, store only metadata in D1 and derived bytes in R2, and require the participant session on every asset fetch; players may view only handouts actually sent to them. Default the handout viewer to a true whole-image Fit mode for portrait and landscape assets, with an explicit scrollable Actual size mode.
- Let the DM optionally Show immediately when sending an attached handout. Apply it only to newly received live messages for connected recipients, queue simultaneous handouts, reset the option after every send, and never change chat unread state merely because the image opened. Offline recipients receive an ordinary unread attachment on return.
- Keep the join surface limited to the four trusted human identities: Dan, Barry, Scott, and Kevin. Do not present a character or role as the login identity; resolve both only after campaign selection. Do not restore free-form name, role, or encounter-code fields unless explicitly requested.
- Authenticate production visitors through Google OpenID Connect with only `openid email profile`: bootstrap the four invited identities by their verified Gmail addresses, then bind the stable Google `sub` to the durable identity. Never let a production visitor choose or submit an identity ID, and never use mutable email as the account's permanent key after linking. Keep the four-person identity switcher strictly localhost-only for testing, use revocable opaque server sessions in HttpOnly SameSite cookies, and derive every campaign and encounter-entry identity from that session. Keep the privacy policy and terms of service publicly accessible without authentication and linked from the sign-in surface so the Google consent and account-entry flow always has usable legal links.
- Keep permission to create campaigns as a durable identity capability distinct from campaign role. Dan, Barry, Scott, and Kevin may create campaigns; the creator becomes that campaign's DM, while DM/player roles and character control remain campaign-scoped memberships. Campaign management may add only invited identities, optionally establish their starter character and combat defaults, and create a fresh first encounter directly from active campaign characters without requiring an older encounter to copy.
- Treat Ember Keep as one encounter, not the application identity. After Google authentication in production, or localhost-only identity selection during testing, show every campaign available through that human's durable campaign memberships; entering a campaign opens its encounter home. Roles and controlled characters come from the selected campaign membership, never from a browser-supplied role or a character-specific login.
- Use Campaign as the top-level game container. A campaign has one party represented by its active campaign characters and memberships, plus multiple encounters. Keep Party as user-facing collective language rather than a separate 1:1 database record until the product genuinely supports multiple parties inside one campaign.
- Treat login and campaign landing as a cinematic threshold into play: use the cohesive full-screen fantasy scene with strong dark readability treatment, reserve its four-adventurer left side on desktop by placing campaign content in the right reading column, and keep mobile content full-width. Show compact waist-up artwork on every Party card, using each campaign character's durable art asset and a dedicated storyteller portrait for the DM.
- Keep the campaign-home encounter area concise: default one compact selector to the most recently updated encounter, show that encounter's status and update time, and keep its available Rename, Set up, and Battle map actions adjacent rather than rendering every encounter as a tall card.
- Keep campaign-home priorities aligned with frequency: Party first, Encounters next, then a compact default-collapsed Combat actions section that summarizes the configured count and expands only for character action maintenance.
- Seed the initial durable campaign as Force of Nature: Kevin is its DM; Dan controls Dar'eleth, Barry controls Jelton, and Scott controls Malichar. Those relationships are campaign-scoped data, not global name-based ownership rules, so one human can eventually hold different roles and characters in different campaigns.
- Encounter creation is a DM-only campaign-home workflow and must not require opening an active encounter first. Fresh encounters copy the selected campaign's active player characters at full health; duplication copies the selected source map and tokens. Both stay in the same campaign, start in setup with combat, initiative, effects, movement, and history cleared, and immediately appear in the DM's encounter list.
- Encounter renaming is a DM-only campaign-home workflow. Rename only the durable display name and keep the encounter code stable so its map, tokens, combat state, and history remain attached.
- Keep encounter preparation distinct from the live battle map. The DM campaign home provides separate Set up and Battle map actions for each encounter; Set up establishes the encounter session and opens the user-facing Encounter Setup draft editor directly, while returning from setup goes back to the encounter list. Encounter Setup owns the private DM briefing and full durable handout-library management. Live chat retains prepared-handout selection and quick upload-and-attach, but the battle map must not expose separate map-workshop, setup, or Encounter Details launchers.
- Identity selection must remain immediate and independent of encounter network requests. Bound encounter-entry requests, restore every encounter action after failure, and show a clear retry message.
- Resolve ownership from durable campaign character controllers rather than browser sessions, global character names, or token IDs. Summons inherit the controller of their root campaign character, non-character tokens default to that campaign's DM, and the DM may control every token. Never restore claim, reconnect, release, unclaimed, or expiring-ownership UI.
- Treat armor class as a private combat stat alongside exact HP: the DM sees every token's AC, while a player receives AC only for their fixed character and summons rooted to that character. Enforce this in the server projection rather than merely hiding it in the client.
- Keep the creature library storage-backed and lazy: searchable metadata belongs in D1, original/thumbnail bytes belong in R2, palette results are paged, thumbnails load only when visible, and full token art loads only for placement previews or tokens on the active map.
- Show the creature palette to players as well as the DM. Every player placement is forcibly created as that player's summon, rooted to their fixed character, sharing that character's initiative, and immediately controlled by that player; only the DM may place unattached monsters or choose a different summoner.
- Treat persistent map spells as first-class shared entities, not annotations: players place them through the spell palette, ownership is rooted to their fixed character, movement is optimistic and server-authoritative, spell motion does not consume creature movement, and controllers may dismiss their own effects. Render animation locally from deterministic shared state so no animation frames cross the network.
- Keep spell placement one-shot: after one click or drag placement, clear the armed spell selection immediately. Creature palette placement remains repeatable.
- Keep generic circle and square spell areas available as fallbacks. Let a spell's controller or the DM resize every persistent spell footprint from 5 to 20 feet after placement while preserving each dedicated spell's established default size.
- Let every participant select persistent map spells and inspect their sidebar cards. Keep non-owner cards read-only; only the spell's controller and the DM may move or dismiss the effect. With a controlled spell selected on the battle map, Delete or Backspace dismisses it through the same action as the card button; dismissal must remain undoable and redoable, and shortcuts must not fire while editing fields.
- Drive attached token VFX from the durable card effect itself. In particular, adding or removing Bless must automatically add or remove one clearly visible but restrained orbiting gold mote with a brief occasional flare, without a second placement workflow; do not add a halo, aura, or dotted ring.
- Present a required concentration check optimistically alongside the initiating participant's HP paint as a blocking shadowbox modal that names the affected token and requires explicit dismissal; reconcile it with the authoritative response without reducing it to a delayed transient corner notice.
- Render Haste from its durable card effect as a discrete blue-white pulse that appears at a deterministic random clock position on the token perimeter, expands and fades completely, then reappears elsewhere after a deterministic 2–3 second interval. Do not rotate, draw a tail, or create a complete ring or constant aura. Attached effect VFX must animate even when no persistent spell object is present.
- Keep Magic Circle's visible artwork on its full 10-foot-radius perimeter with a generous clear interior; compensate for transparent source-image padding rather than sizing only the image box. Render one artwork layer only—never add a smaller rotated echo inside it. Hit-test against the visible ring and prioritize character/creature hits so occupants remain easy to select and move. Do not draw the generic dotted ownership or dashed selection circle over Magic Circle—the artwork is already its boundary.
- Keep native spell-palette drag imagery suppressed with a persistent transparent drag image and disable native dragging on spell artwork, so Moonbeam and Flaming Sphere show only the square, screen-blended map preview instead of a black rectangular palette ghost.
- Let Medium and larger creature artwork fill the complete circular token footprint in both normal and transparent-center display modes, while Small creature art is intentionally inset to 75% within its mechanically full 5-foot token. Keep Large, Huge, and Gargantuan token outlines especially restrained so the art remains visually dominant.
- Creature catalog records must carry placement-ready defaults: average HP, hit dice, AC, challenge rating, creature type, size, and separate walk/fly/swim/climb/burrow speeds. Placement initializes current and maximum HP from the catalog default.

- Grow the production creature catalog through the secret-protected batch importer in groups of at most ten; never commit its bearer token or authorize imports through the selectable DM role.
- Load staged combat-action enrichment through the action-only catalog importer in groups of at most ten. Require a complete server dry run and verified production backup before `--apply`; replace only action profiles, and never rewrite creature metadata or R2 artwork in that workflow.
