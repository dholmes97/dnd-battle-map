## Executive summary

The review records **98 confirmed findings**: **1 Critical, 21 High, 54 Medium, and 22 Low**. The count intentionally includes the 34-item security set and 64 broader engineering/product findings; several share a remediation program, so this is a finding count rather than 98 independent projects. The strongest positive is a meaningful framework-free shared core with 182 passing local tests and stable high-resolution map geometry. The dominant systemic risk is that the public accountless identity model is implemented as caller-selected authorization, while state changes that should be one transaction are split across D1/R2 writes, version bumps, and history rows. The client then compounds those risks with fragile optimistic recovery and little browser-level protection for its most complex UI.

### Recommended remediation order

1. **Stop identity takeover and principal confusion:** replace self-asserted join roles/names (SEC-01) with fixed, server-issued identity capabilities; migrate token/summoner ownership to immutable keys (SEC-33); require sessions on state/events and protect hidden-token/spell identifiers.
2. ✅ ~~**Close persistent denial-of-service inputs:** cap bodies before parsing, bound every collection/write, validate both annotation endpoints (SEC-02/03/19/23/24/34), and add rate/concurrency controls.~~ **Completed and verified 2026-08-21.**
3. **Restore state integrity:** remove the zero-token sentinel (REL-05), introduce an atomic D1 unit of work for mutation/version/history (REL-03/ARCH-02), enforce valid combat transitions (RULE-03), and resolve scenario/handout/provisioning races and R2 cleanup through idempotent intents/outboxes.
4. **Make optimistic UI failure-safe:** guarantee rollback or authoritative replacement after every rejection/timeout (UX-02/REL-02), serialize/reconcile operation IDs, and add the deferred-promise interleaving suite in TEST-04 before expanding optimistic behavior.
5. **Repair release controls:** fix Drizzle snapshots (REL-01), upgrade/triage the vulnerable dependency graph (DEP-01), and establish CI for typecheck, lint, tests, build, migration drift, authored-source coverage, accessibility/browser flows, asset/docs integrity, and advisory review (OPS-01/TEST-01/08).
6. **Address highest-impact play UX:** fix mobile settings/chat/palettes (UX-05/07/08), workshop draft loss and destructive annotation clearing (UX-09/11), dialog focus and keyboard-equivalent map/workshop controls (A11Y-03/04/05), then token label crowding and target/readability issues.
7. **Pay down performance and operability debt:** stop token-art reloads and needless static-spell animation, reduce token assets, replace one-second idle polling, optimize projections/indexes, offload handout transcoding, split composition roots/controllers/styles, add error boundaries and structured correlation-aware telemetry.

SEC-33 was validated during the subsequent authorization/domain pass and is outside the sealed 32-finding scanner artifact. `shared/token-control.ts:9-16` recognizes the three original token IDs, but otherwise assigns Dan, Barry, or Scott solely when a token's mutable display name exactly equals `Dar'eleth`, `Jelton`, or `Malichar`. Fresh and duplicated scenarios generate new token IDs and leave ownership fields null (`worker/adapters/d1-scenario-map-repository.ts:43-75`), making that display name the only player-authorization key. Renaming one's character causes the next request to resolve it to Kevin and removes the player's control/private-stat access; naming an unrelated monster after a character grants the corresponding player control plus private HP/AC projection. `tests/token-control.test.mjs:13-15` currently codifies this unsafe fallback. SEC-34 was likewise validated after the sealed scan. `add-annotation` bounds only the first `(x,y)` point; `x2` and `y2` need merely be finite, so values up to approximately `1e308` are accepted from any player and stored durably. Every participant receives the row and `app/battle-map-renderer.ts:612-614` multiplies the endpoint through viewport transforms before passing it to the canvas path; geometry hit-testing also consumes it. Depending on browser numeric handling this can produce infinities, break hit testing, or repeatedly throw/abort shared-map rendering, yielding a persistent cross-client denial of service until a DM clears annotations. Validate both endpoints as a complete pair within grid bounds, cap segment length/precision, defensively reject invalid projected rows, and add malicious-command plus renderer-regression tests.

### Security hardening outside the canonical finding set

#### HARD-01 — The application defines no browser security-header policy (Low)

No authored response path or deployment configuration sets a Content Security Policy, `frame-ancestors`, `X-Content-Type-Options` globally, Referrer Policy, or Permissions Policy. A few binary asset responses correctly set `nosniff`, and the hosting edge may add transport headers, but there is no repository-owned and testable policy for the HTML/application surface. React escaping and the absence of authored raw-HTML sinks reduce immediate XSS reachability, so this is defense in depth rather than a newly demonstrated exploit. Still, the app exposes consequential DM actions and should not be freely frameable. Add a conservative CSP (at minimum `default-src`, explicit image/font/connect allowances, `object-src 'none'`, `base-uri 'self'`, and `frame-ancestors 'none'`) plus consistent hardening headers at the Worker response boundary; verify the production response and add an integration contract so framework/hosting changes cannot silently remove them.

### UI/UX and behavior

#### UX-01 — Ordinary tokens cannot be selected while movement is unavailable (Medium)

`app/use-battle-map-gestures.ts:394-403` resolves the hit token, then returns early whenever `movementEnabled` is false. The early branch selects only persistent spell effects; ordinary characters, summons, and monsters are ignored. The normal selection path does not run until `app/use-battle-map-gestures.ts:429-432`, after that return. Because `movementEnabled` is false while the encounter is paused, the connection is not live, or the root adapter is busy, users cannot inspect ordinary token cards in exactly the states where movement—not selection—should be disabled. This contradicts the product invariant that selection is independent from movement authority and creates inconsistent behavior because spell effects remain selectable. Move selection before the movement gate, then gate only drag/placement actions. Add a component contract covering paused, reconnecting, busy, strict-movement, foreign-token, and spell-effect selection.

#### UX-02 — Rejected optimistic actions can remain painted indefinitely (High)

`app/use-encounter-sync.ts:320-370` paints an optimistic mutation and, on rejection, deletes only its bookkeeping entry; it does **not** synchronously restore the pre-mutation state. Token movement uses the same pattern at `app/use-encounter-sync.ts:421-480`. Both paths depend on `refreshAfterError()` fetching authoritative state, but that refresh swallows failure and leaves the current React state untouched at lines 280-286. A rejection commonly coincides with a network or server problem, so the follow-up request can also fail: the UI then continues showing an action the server rejected (including token creation/deletion, HP, effects, initiative, map edits, and movement) until some later live poll succeeds. This violates the explicit optimistic-interaction invariant to roll back the rejected mutation. Capture an inverse/pre-mutation state for every pending operation, remove only the rejected reducer, and synchronously recompute visible state from the last authoritative snapshot plus the still-pending reducers; use refresh only for reconciliation. Add tests where both the command and recovery fetch fail, including two concurrent mutations where only one is rejected.

#### UX-03 — User-facing metadata still presents the production app as a prototype (Low)

The root metadata describes the application as a “focused proof” (`app/layout.tsx:20-21`) and the page metadata calls it a “battle-map prototype” (`app/page.tsx:4-7`). The package is named `dnd-battle-map-poc`, and the main component is `BattleMapPrototype`, even though the README and implementation describe a durable multi-scenario production application at the canonical domain. Browser history, link previews, accessibility tooling, and search/OS surfaces consume this metadata, so users receive an outdated product identity. Rename the user-facing metadata now; internal identifiers can be migrated separately if churn is not worthwhile.

### Performance

#### PERF-01 — Every encounter-state token-array replacement reloads all token artwork (Medium)

`app/use-map-assets.ts:58-64` derives the distinct artwork paths but keys the loading effect to `state?.tokens` object identity. Every authoritative state projection supplies a new token array, so HP, initiative, effects, annotations, chat, fog, and other unrelated shared updates construct fresh `Image` objects for every visible token asset and replace the complete `tokenArt` map. Browser HTTP caching may avoid transferred bytes, but it does not avoid repeated image object creation, decode/cache churn, promises, state updates, and redraws. This is the token-art equivalent of the response-identity scene reload that `app/use-map-assets.ts:41-56` correctly avoids for the base map. Derive a stable sorted asset-key fingerprint, retain loaded images by path, load only additions, and release only removed assets. Add a hook test proving that unchanged artwork is not reloaded across state-array replacements.

#### PERF-02 — Static generic spell shapes keep the full canvas repainting at 24 FPS (Medium)

`app/use-map-assets.ts:80-90` treats the presence of any `spell-effect` token as animated and keeps scheduling full `drawMap` calls at 24 FPS. `shared/spell-effects.ts:49-67` defines generic circle and square fallbacks, while `app/battle-map-renderer.ts:169-192` renders those shapes without using animation time; they are static. A single generic spell therefore keeps the complete base map, fog mask, grid, annotations, all spells, all creature tokens, labels, health rings, and effects repainting indefinitely for no visible change. Drive the loop from an explicit animation capability (dedicated animated spell IDs, transient pings/spotlights, Bless/Haste), and render generic shapes only on state/viewport changes. Add a reduced-motion and static-spell animation-scheduling contract.

#### PERF-03 — Changed encounter projections combine unbounded reads with quadratic effect attachment (Medium)

`worker/index.ts:959-1021` loads all tokens, effects, annotations, DM handouts, and up to 60 presets into one request; only chat and presets are bounded. `worker/index.ts:1072-1115` then runs `effects.results.filter(...)` independently for every visible token, making effect attachment O(tokens × effects). The short-circuit for unchanged event polls is valuable, but every shared version change still pays this cost separately for each connected viewer, and direct state reads always build the projection. This compounds SEC-03 and SEC-23. Enforce scenario cardinality limits, index effects by `token_id` once, split or page preparation-only collections, and measure/query-budget the changed-state path with realistic large encounters.

#### PERF-04 — Two repeated lookup paths cannot use the available indexes efficiently (Low)

`worker/adapters/d1-token-effect-repository.ts:81-85` checks concentration with `WHERE token_id = ? AND effect_type = 'concentration'`, but the only effects index is `(encounter_id, token_id)` (`db/schema.ts:257-259`); SQLite cannot use the second column of that index as the lookup prefix. Every damage action therefore scans the effects table. Likewise, every player handout image fetch runs a delivery lookup by `(encounter_id, handout_id)` at `worker/index.ts:897-905`, while the chat index is `(encounter_id, created_at, id)` (`db/schema.ts:352-357`), forcing a scenario-chat scan for each image request. These tables are durable and unbounded, so the cost grows with campaign history. Pass `encounter_id` to the concentration lookup and add an appropriate effect-type suffix/index; add `(encounter_id, handout_id, created_at)` (ideally partial for non-null handouts) for delivery checks. Lock both down with `EXPLAIN QUERY PLAN` migration tests.

#### PERF-05 — Idle clients continuously spend one Worker request and D1 lookup per second (Medium)

`shared/live-polling.ts` backs off only to one second, while `app/use-encounter-sync.ts:216-236` keeps the loop active for every visible encounter. The Worker short-circuits unchanged event polls before loading full collections (`worker/index.ts:1248-1264`), which is valuable, but it still authenticates and reads encounter/version state for each request. Local runtime logs confirmed the steady one-request-per-second cadence; four connected participants therefore produce roughly 14,400 Worker invocations per idle hour before 20-second heartbeats and any real commands. The live concurrency test passed and measured 30.1 requests/second only because its manual harness polls every 250ms, not because the product does. Adopt long polling, Server-Sent Events, WebSockets/Durable Objects, or at least a materially longer jittered idle backoff with immediate revalidation on visibility/focus; measure both invocation and D1 costs for the actual four-person workload.

#### PERF-06 — Built-in token art is orders of magnitude larger than its rendered footprint (Medium)

The 20 PNG files under `public/assets/tokens/` total 26,686,284 bytes (about 1.33 MB each on average); sampled assets are 1,254×1,254 pixels. On the map they commonly render at roughly 30–100 CSS pixels, and the sidebar also loads these originals. Loading all 20 implies about 125 MB of decoded RGBA pixels before browser overhead, even though most of that resolution is never displayed. The complete public directory is 78 MB and the production build is 103 MB, dominated by 49 MB of deliberately high-resolution scene maps and this 26 MB token set; unlike maps, tokens have no requirement to preserve 128 source pixels per grid cell. Generate versioned WebP/AVIF map and card variants (with a reasonable PNG fallback), use responsive dimensions, and keep full resolution only where an actual zoom/detail view needs it. Add an asset-budget test for encoded bytes, decoded dimensions, and catalog-manifest coverage.

#### PERF-07 — Login and campaign-home users eagerly download the encounter and workshop application (Low)

`app/battle-map-prototype.tsx:8-30` statically imports Map Workshop, chat, both palettes, dialogs, renderer-facing hooks, and the encounter shell even when the user is still choosing an identity or viewing the campaign home. The authored client JavaScript is not yet enormous (approximately 505 KB raw across the main framework, battle-map, and index chunks; about 152 KB for a concatenated gzip diagnostic), but the costly feature boundary is already clear and will keep growing. Dynamically load the encounter shell after scenario entry and lazy-load preparation/chat/palette features at first use; retain small shared domain helpers outside those adapter chunks. Track route/state-specific transferred and executed JavaScript in the build gate.

#### PERF-08 — Every Undo/Redo scans encounter-wide history before filtering the participant (Low)

`d1-history-repository.ts:9-13` queries `actions` by both `encounter_id` and `participant_id`, ordered by time, but `db/schema.ts:288-305` provides only `(encounter_id, created_at)`. #### PERF-09 — Handout preparation can monopolize memory and the browser main thread (Medium)

The browser accepts images up to 24 megapixels (`shared/handout-domain.ts:3-5`), decodes the entire original with `createImageBitmap`, creates separate display and thumbnail canvases, and performs repeated full-canvas `toBlob` encodes across as many as six quality levels per format (`app/handout-images.tsx:85-145`). A maximum-size decode alone is roughly 96 MB of pixel memory before the 2,048px display canvas, thumbnail, encoded blobs, and browser internals; WebP failure can repeat the quality search in JPEG. `db/schema.ts:197-235` stores `tokens.summoner_token_id` without a foreign key or deletion policy, and `worker/adapters/d1-token-effect-repository.ts:165+` deletes only the selected token. Summons and persistent spells can therefore keep a nonexistent root ID. `shared/token-control.ts:18-25` cannot resolve the missing summoner and falls back to the child token, which normally maps to Kevin, so the player permanently loses control while the orphan remains on the shared map. Choose and enforce a domain policy—block root deletion, cascade the rooted entities, or reassign them atomically—add a self-referential foreign key where D1 migration constraints permit, and cover deletion/undo/redo plus legacy-orphan repair.

#### RULE-03 — Setup can be paused and then resumed into invalid active combat (High)

The DM sidebar enables **Pause** even when `inCombat` is false (`app/encounter-sidebar.tsx:151-152`). It sends `configure-encounter {status:"paused"}`, and a second click sends `status:"active"`. The command accepts every status without validating the current transition (`worker/commands/scenario-map-commands.ts:189-198`); the D1 adapter's non-setup branch changes only the status. A setup encounter can therefore become active with round 0, no active initiative order, and no start-combat initialization, after which movement/turn controls operate against incoherent state. Make transitions explicit in the framework-free core: setup may start only through `start-combat`; only active may pause; only a paused, previously initialized combat may resume; reset is the only transition to setup. Enforce server-side and disable the irrelevant control in setup.

#### RULE-04 — Non-reversible activity silently evicts durable Undo history (Medium)

Undo reconstructs its stack from the newest 200 raw participant action rows (`worker/adapters/d1-history-repository.ts:9-13`) and only then removes non-reversible entries. Pings and both spotlight styles intentionally record actions but are excluded from Undo; after 200 such transient actions, an otherwise valid recent drawing/move/HP edit falls outside the query and the UI claims there is no reversible action in the participant's ten-step history. The same truncation can orphan older undo/redo markers from the action they reference. Persist the bounded authoritative undo/redo stacks directly, or query/reconstruct enough reversible actions and their markers without letting excluded activity consume the window; add a regression with more than 200 pings around ten durable edits.

#### REL-04 — Handout deletion destroys R2 objects before D1 records the tombstone (Medium)

`worker/commands/chat-handout-commands.ts:63-65` deletes both object keys first and only then marks the handout deleted in D1. If either parallel R2 delete partly fails, or if the subsequent D1 update/version bump fails, durable live metadata and historical chat references continue advertising a handout whose display and/or thumbnail bytes are gone. The operation is neither atomic nor recoverable, and retry behavior cannot distinguish already-missing objects from an uncommitted delete. First commit an idempotent deletion intent/tombstone with an outbox/cleanup record, hide the asset from delivery, delete objects idempotently, and finalize; a retry/garbage-collection worker should reconcile every intermediate state. Inject failure before, between, and after the two storage deletes and D1 stages.

#### DATA-03 — Core database invariants exist only in TypeScript, not in D1 (Low)

The schema uses free-form text for encounter status, role, token kind/size, fog-adjacent record types, effect/reminder types, and multiple state flags; it also has no checks for positive grid dimensions, HP bounds, initiative ranges, movement/altitude, asset byte dimensions, or nonnegative catalog stats. Most normal command paths validate these values, but history replay, migrations, import/provisioning scripts, and direct operational writes are parallel mutation paths and already duplicate validation. A single bug can persist a state that every reader assumes is valid. Add pragmatic `CHECK` constraints for closed enums and cheap scalar invariants, retain domain validation for cross-row rules, and include rejection plus legacy-data migration tests.

#### REL-05 — Deleting the last token permanently bricks an otherwise valid scenario (High)

After loading a confirmed encounter and all of its collections, `worker/index.ts:1027` returns `null` solely when `tokens.results.length === 0`. The DM is authorized to delete ordinary tokens, including the final one. That delete commits and bumps version, then the command response obtains `state: null` despite the `CommandResponse` contract; the client passes it to `acceptAuthoritativeState`, which dereferences `next.encounter`. Every later state/join request also reports the existing scenario as not found, leaving no UI path to add a replacement token. An empty setup map is a valid preparation state and must project normally. Remove the token-count sentinel, keep encounter existence as the only not-found test, harden client response validation, and add adapter/live tests that delete all tokens, reload, place a new creature, and undo/redo safely.

#### REL-06 — A feature exception can take down the whole client with no recovery boundary (Medium)

The App Router contains only `layout.tsx` and `page.tsx`; there is no route `error.tsx`, global error boundary, or feature-level boundary around the map, workshop, chat, palettes, or sidebars. The canvas path invokes `drawMap` directly from React effects, `ResizeObserver`, and animation frames (`app/use-map-assets.ts:66-89`) without isolating malformed projection data, numeric/canvas failures, or browser-specific exceptions. A bad durable row such as SEC-34, an unexpected response shape such as REL-05, or a renderer defect can therefore replace or disable the entire encounter rather than degrading one feature and offering reload/retry diagnostics. Add a route recovery boundary plus a narrower encounter/canvas boundary, preserve a privacy-safe correlation ID and last known connection state, and test render/effect/observer exceptions with recovery, reload, and return-to-campaign actions.

### Operations and observability

#### OPS-01 — The repository has no automated CI or dependency/update gate (High)

There is no `.github/workflows` configuration and no equivalent checked-in CI definition, dependency update policy, CODEOWNERS, or security policy. The local default suite is useful and currently green, but nothing in the repository requires typecheck, lint, Node tests, component tests, build, migration apply, Drizzle no-op generation, coverage, or advisory triage before merge/deploy. DEP-01 and REL-01 are exactly the kinds of drift an automated gate should surface. Add a least-privilege CI workflow with locked installs, separate fast and integration jobs, migration/schema drift checks, authored-source coverage artifacts, asset/document integrity checks, and a dependency advisory policy that distinguishes reachable production risks from build-only exposure. Document the required branch/deployment checks.

#### OBS-01 — Failures are logged without enough context to diagnose shared-state incidents (Low)

Platform observability is enabled in generated Wrangler metadata, but application logging is mostly ad-hoc `console.error(label, error)` at broad route boundaries. There is no consistent request/correlation ID, encounter/action identifier, participant role, latency/query count, optimistic command sequence, or structured error classification, and client polling deliberately swallows errors. When a participant reports a stuck optimistic move, stale version, failed history action, or provisioning race, logs cannot reliably correlate browser action, Worker request, D1 commit stages, and recovery poll. Define a privacy-conscious structured event schema, propagate a request/operation ID through responses and client notices, record bounded timings/outcomes at port boundaries, and add health/SLO dashboards or alerts for command failures, poll volume, projection latency, and provisioning/backup integrity.

#### OPS-02 — An ignored local script performs bulk production deletion by default (High)

`.working/delete-production-old-style-presets.mjs` is outside version control and ordinary review, but its default path joins production by self-asserting a new DM identity, enumerates presets, and deletes all 26 when a brittle count/type guard happens to match. Only `--verify` is non-destructive—the safe and dangerous defaults are inverted. It targets the retired generated Sites hostname rather than the canonical origin, has no explicit `--execute` acknowledgement, typed scenario/target confirmation, existing authorized credential, verified-backup requirement, or recovery manifest. This is both a practical exploit demonstration for SEC-01 and a high-risk operational footgun. Remove it after use or move a hardened, reviewed migration/maintenance tool into `scripts/`; make audit the default, require a specific execute flag and canonical target, authenticate through a dedicated bounded capability, capture exact IDs, and enforce the project's backup policy before deletion.

#### PRIV-01 — Private provisioning jobs and mailbox metadata have no retention lifecycle (Medium)

The ignored `.working/scenario-email/` tree still contains a completed envelope, provider message/thread identifiers, normalized sender address, DM-only briefing, source images, prepared handouts, map assets, and creature art days after provisioning. The skill correctly calls this a private temporary job directory and prevents Git inclusion, but its workflow has no successful-job cleanup, retention duration, permission verification, or failure quarantine policy. `.gitignore` is not a confidentiality boundary; persistent mailbox and campaign data can leak through machine backups, support bundles, or later local tooling. Use a permission-restricted temporary/job root outside the repository, retain only a minimal non-secret reconciliation record, securely remove derived/source assets after a bounded success period, and document explicit retention for failed jobs needed for retry.

#### DX-01 — Binary history and ignored working assets consume gigabytes without lifecycle tooling (Medium)

The current `.git` object store is about 645 MB with no packs, while the current public surface is about 78 MB. Reachable history contains many retired multi-megabyte terrain/stamp PNGs and superseded full-scene images; there is no Git LFS/attributes policy. Two unused generated handout originals (about 6.5 MB total) remain tracked under `materials/` with no code references, while ignored `catalog/art/` and `.working/` consume roughly 1.2 GB and 942 MB locally. Versioned filenames are required for immutable browser/R2 caching, but retaining every large binary in normal Git and indefinitely retaining generated working sets are separate choices. Define source/derived/production-asset ownership, use LFS or external content-addressed storage where appropriate, remove orphan tracked sources after confirming provenance needs, and add cleanup/status tooling plus documented local retention budgets.

#### OPS-03 — Catalog builder network and output behavior is not reproducible or failure-hardened (Low)

`scripts/build-creature-catalog.mjs` and `scripts/build-creature-expansion.mjs` fetch mutable third-party APIs without timeouts, retries, response-byte limits, response hashes, or immutable source snapshots. They then write the canonical JSON output path directly rather than a temporary file plus atomic rename. A stalled API can hang the workflow, upstream pagination/content changes make regeneration non-reproducible despite a hard-coded research date, and interruption during the final write can truncate a previously valid catalog. Add bounded fetch/retry helpers, record response/version/checksum evidence and licensing metadata, validate the complete temporary output, then atomically replace only on success.

### Catalog data and documentation

#### DATA-01 — Third-party creature provenance is discarded during import and omitted from the catalog documentation (Medium)

`catalog/creatures-expansion-1000.json` contains 500 records: 52 from SRD 5.2 and **448 from four Kobold Press documents** (`ccdx`, `tob-2023`, `tob2`, and `tob3`). The source records retain document name, publisher, and API URL, but none retains a license or attribution text. More importantly, `worker/index.ts:614-681` deliberately selects only gameplay/art fields into `prepared`; the D1 `creature_catalog` schema has no provenance or attribution columns, and the API response at `worker/index.ts:546-566` cannot expose them. Once imported, provenance is therefore irreversibly detached from each production record. `docs/CREATURE-CATALOG.md:3-7` describes standard metadata as coming from the D&D SRD and attributes only Wizards of the Coast, even though the checked-in expansion contains mostly non-SRD metadata. This is a traceability and license-compliance risk, not a legal conclusion about the underlying terms. Preserve source document key/name/publisher/license/URL in D1, expose appropriate attribution in the product or a durable notices surface, and make tests require license metadata for every non-original catalog entry.

#### DOC-01 — Operational documentation overstates security and atomicity guarantees (Medium)

Several statements read as verified controls but are contradicted by implementation. `README.md:10` says identities are fixed although the join API accepts caller-selected names and roles (SEC-01). `README.md:68-71` says the provisioning workflow uses a sender allowlist and is atomic; `docs/DM-EMAIL-SCENARIO-PROVISIONING.md:104-119` says the API itself requires that allowlist and stages immutable assets. In reality the service validates a manifest-asserted sender (SEC-10), finalization has revision/reference races (SEC-16/18/26), and staged objects have no implemented bounded cleanup (SEC-15/21). `docs/ARCHITECTURE.md:52-54` also promises that the Worker “rolls back only the affected operation,” while UX-02 shows the client can retain rejected paint. Documentation that describes a desired invariant should label it as a target until a test proves it; security/runbook documents especially must distinguish orchestration assumptions from server-enforced controls.

#### DOC-02 — Token-art provenance inventory is stale by more than threefold (Low)

`public/assets/tokens/README.md:3` says the initial library contains six assets. The adjacent `manifest.json` declares 20 assets and the directory contains three characters plus seventeen creature/monster PNGs. The same README directs readers to that manifest as the authoritative file inventory. Update the count or avoid a hard-coded count entirely; add a small manifest-to-files contract that verifies every declared path exists and every shipped PNG is declared.
